# 批量生成的尾帧承接修复（2026-09-22）

## 问题和原因
批量提交循环为全部任务建立执行快照。当上一任务尚无视频时，后续任务被永久快照为“不承接”。视频队列虽然串行执行，却不会在执行前重新取得上一任务结果。

## 当前规则
- 连续选中、通过提交校验的任务，按故事顺序提交。尾帧承接任务绑定上一任务本次提交的 Job ID；不读取任意最新结果，不误用旧结果。
- 提交时冻结提示词、资产、生成参数、工作流和依赖关系。执行前另行一次性保存 execution_context，其中包含实际来源结果、尾帧媒体路径及摘要。原提交快照不被改写。
- 依赖未完成时保持排队，显示“等待上一任务结果”，不显示缺失上下文风险。排序不能越过依赖；挂起来源不占住执行线程，独立任务可以继续。
- 来源成功后唤醒后续任务。重启从持久化依赖恢复，已绑定的执行上下文不重新选取。
- 来源失败、取消、移除或媒体无法读取时，后续任务挂起，在生成前提示风险。运行中心提供“继续生成（不承接）”，明确选择后才不承接执行。
- 不连续选中、上一任务不在本批次或被预检跳过时，维持单任务原有的生成前风险提示和允许直接生成行为。
- 提示词增强与审核始终可选。

## 验证
回归用真实视频文件提取尾帧、模拟生成服务验证三任务链、逆序选择、调序、多 worker、挂起/恢复、重启、来源失败/移除、部分选择、旧结果隔离及冻结输入。并验证运行中心等待和风险操作文案。
不等同于重新运行真实 GPU 视频生成；本次不主动启动用户的电影批次。

既有 Job 的提交快照不追溯改写。升级前已经排队的旧任务若需新承接行为，应移出后重新提交；本次本机升级时不存在这类活动任务。


## 全量检查中发现的历史 UI 测试问题
- 旧播放器测试仅定位一个 video，而当前播放器有活动与预加载两个 video，测试改为活动播放层，保留播放及键盘焦点验证。
- 批量操作入口、全局运行中心、可选审核已由此前需求改变，更新用例入口及预期；保留失败重试、未提交前确认和历史记录验证。
- 小窗口中 Dialog 的宽高预留 32px，但外层 padding 为 24px，导致实际可用区域不足，文本聚焦触发整个外框位移。外层统一为 16px，保留窄屏 8px 规则；验证长文本滚动时外框不移动。
- 日期为用户指定 80% 透明度，对比度测量补充透明纯文字叶节点的 alpha 合成；不修改日期外观、不降低对比度阈值。
