# 1. V0.4 核心目标

## 1.1 用户生产路径

目标用户路径固定为：

```text
项目工作台
  ↓
选择全部或部分 Task
  ↓
批量 AI 提示词增强
  ↓
Prompt Enhancement Queue 顺序执行
  ↓
任务进入“待检查”
  ↓
用户逐一检查 / 修改提示词
  ↓
确认提示词
  ↓
任务进入“已检查 / 可生成”
  ↓
批量视频生成
  ↓
Video Generation Queue
```

AI 负责批量准备 Prompt，人负责最终确认；未经人工确认的任务默认不能被批量送入视频生成。

## 1.2 默认 Prompt AI

V0.4 默认本地 Prompt AI Profile 使用 **Qwen3.8**。

但必须遵守以下边界：

- Qwen3.8 是 Provider / Profile 层默认选择，不进入 Task Domain；
- Core 不得出现 `if model == qwen...`；
- Prompt Enhancement Service 仍依赖抽象 Prompt AI Provider；
- 后续切换其他本地模型或远程 OpenAI-compatible Provider，不得修改 Task / Revision 领域结构；
- 模型文件路径、量化格式、Runtime 参数属于 Provider Profile / Settings，不进入普通业务对象。

## 1.3 V0.4 必须达到

- 支持多 Task 批量 AI Prompt Enhancement；
- 单任务 AI 增强行为保持不变；
- 批量增强使用正式持久化队列，不由 React 做 `for` 循环；
- 批量任务提交时冻结 Prompt Enhancement 输入快照；
- 增强完成后进入人工审核状态；
- 支持“确认并下一个”的连续审核体验；
- 修改已确认的有效 Prompt 后，审核状态自动失效；
- 支持只将已审核且合法的 Task 批量送入 Video Generation Queue；
- Prompt Queue 与 Video Queue 独立，可并行存在；
- Runtime Read Model 可同时描述 Prompt 与 Video 两类后台工作；
- 桌面 UI 完成对应批量操作与审核流程打磨；
- 测试覆盖队列、快照、审核失效、批量生成 Gate 与失败恢复。

# 2. V0.4 明确不做

本版本不要把批量能力扩张成复杂工作流编排系统。

明确不引入：

- DAG 工作流编辑器；
- Redis / Celery / Kafka；
- 分布式 Scheduler；
- 多机 GPU 调度；
- 自动跳过人工审核并直接批量生成的默认模式；
- 自动让 AI 判断“Prompt 已经合格”；
- 为批量功能复制第二套 Prompt Enhancement Service；
- 在 React 中维护真实后台队列状态；
- 为了显示状态堆叠大量 Badge / Pill / 工程术语。

第一阶段仍使用模块化单体 + SQLite + 单机 Worker。

# 3. 状态模型

V0.4 必须明确区分以下三个维度，禁止压成一个 `status`：

```text
Task 内容状态
Prompt 审核状态
生成运行状态
```

## 3.1 Prompt Review Status

新增领域语义：

```text
PromptReviewStatus
├─ not_ready       # 当前没有可审核的有效 Prompt
├─ pending_review  # 已有候选 Prompt，等待人工检查
└─ approved        # 当前有效 Prompt 已被人工确认
```

UI 可使用更自然的中文：

```text
AI 未增强
增强中…
待检查
已检查
```

UI 文案不要求与 Domain enum 一一对应。

## 3.2 审核对象

审核针对的是**当前真正会用于生成的 Prompt 内容**，而不是笼统针对整个 Task。

确认时至少记录：

```text
approved_prompt_source
approved_prompt_hash
approved_at
```

可选记录：

```text
approved_revision_id?
```

这样可以明确判断当前 Prompt 是否仍等于用户当时确认的版本。

## 3.3 审核失效规则

以下行为必须使 `approved` 自动回到 `pending_review` 或 `not_ready`：

- 再次执行 AI 增强并产生新的当前 AI Prompt；
- 用户编辑当前被采用的 Prompt 文本；
- 用户从 user Prompt 切换到 ai Prompt，或反向切换；
- 切换到不同 AI Prompt Revision；
- 会影响最终 Prompt 语义的自动处理发生变化。

以下行为不应无意义地使审核失效：

- 只切换可视化 / 文本显示模式；
- 修改 Task 标题；
- 修改不参与最终 Prompt 的纯 UI 偏好。

审核失效应通过 Prompt Source + 内容 hash 判断，不要依赖 React 猜测。

# 4. Prompt Enhancement Batch / Queue

## 4.1 Batch 是用户一次批量操作

建议领域对象：

```text
PromptEnhancementBatch
├─ id
├─ project_id
├─ status
├─ total_count
├─ queued_count
├─ running_count
├─ completed_count
├─ failed_count
├─ cancelled_count
├─ created_at
├─ started_at?
└─ finished_at?
```

Batch 用于汇总与 UI 展示；真正执行单位是 Prompt Enhancement Job。

## 4.2 Prompt Enhancement Job

建议结构：

```text
PromptEnhancementJob
├─ id
├─ batch_id
├─ project_id
├─ task_id
├─ status
├─ source_snapshot
├─ context_snapshot
├─ provider_profile_snapshot
├─ target_skill
├─ created_at
├─ started_at?
├─ finished_at?
├─ revision_id?
└─ error?
```

状态至少：

```text
queued
running
completed
failed
cancelled
```

## 4.3 不可变输入快照

Task 是可修改的，队列 Job 是一次已提交工作。

批量提交时冻结至少：

- Task ID；
- 用户描述 / 当前用户 Prompt；
- 当时绑定的媒体 Asset ID 与 role；
- 目标 Prompt Skill；
- 项目背景是否启用，以及使用的项目背景正文；
- 上一任务摘要是否启用，以及使用的摘要正文；
- generation context 中 Prompt Enhancement 真正需要的限制；
- Prompt AI Provider Profile；
- 模型标识；
- Story Order / previousTaskId 解析结果。

用户在 Job 已进入队列后修改 Task，不得静默改变该 Job 的语义。若需要使用新内容，应重新入队。

## 4.4 顺序

默认按项目当前 Story Order / Task Order 执行。

原因：上一任务摘要可能参与后续任务 Prompt Enhancement，保持稳定的故事顺序更符合用户预期。

第一版无需自动把前一个刚生成的 AI Prompt 传给后一个任务。仍然遵守既有架构：上一任务可选上下文默认是 **Task Summary**，不是上一任务完整 Prompt。

## 4.5 并发

V0.4 默认：

```text
prompt_enhancement_max_concurrency = 1
```

原因是默认目标为本地 Qwen3.8，第一版优先稳定性与显存 / 内存可控性。

Scheduler 与模型无关，配置层应保留未来设置为 2 / 4 / 8 的可能。

## 4.6 单任务增强保持不变

现有接口 / 行为必须继续成立：

```text
打开 Task Editor
→ 点击“增强”
→ 产生 AiPromptRevision
→ 当前 AI Prompt 更新
→ 用户继续编辑 / 选择历史
```

批量增强与单任务增强最终都调用同一 `PromptEnhancementService` / Skill / Provider 能力。

禁止：

```text
single_enhance.py
batch_enhance.py
```

各实现一套 Prompt 逻辑。

# 5. Batch Prompt Enhancement Application Flow

推荐 Application 流程：

```text
create_batch(project_id, task_ids, options)
  ↓
validate task ownership / order
  ↓
freeze each input snapshot
  ↓
persist Batch + Jobs
  ↓
Scheduler claims queued Job
  ↓
PromptEnhancementService.enhance_from_snapshot(...)
  ↓
AiPromptRevision
  ↓
Task current AI Prompt / revision 更新
  ↓
PromptReviewStatus = pending_review
  ↓
emit runtime event
```

单个 Job 失败不得阻止整个 Batch 继续处理后续任务。

Batch 最终可为：

```text
completed       # 全部成功
completed_with_errors
cancelled
```

具体 enum 可在实现时收敛，但 UI 必须能区分“全部完成”和“部分失败”。

# 6. 取消、重试与失败

## 6.1 取消

第一版至少支持：

- 取消仍处于 queued 的 Job；
- 取消 Batch 时阻止新的 queued Job 开始；
- 当前正在运行的本地模型请求如果 Provider 无安全中断能力，可以允许当前项完成后停止。

UI 不应声称已中断一个实际上无法中断的推理。

## 6.2 重试

失败项允许：

```text
仅重试失败任务
```

重试应创建新的 Job attempt 或新 Job 记录，不覆盖旧失败记录。

## 6.3 幂等与重复点击

同一 Task 在已经有 Prompt Enhancement Job `queued/running` 时，再次批量提交必须明确处理：

- 默认跳过并在预览中告知；或
- 明确允许创建后续 Job。

V0.4 推荐默认 **跳过已有 active prompt job 的 Task**，避免用户误双击造成重复本地推理。

单任务“增强”按钮在当前 Task 正在批量增强时也应显示忙碌状态并禁止重复提交。

# 7. Prompt Review / 人工检查

## 7.1 确认动作

新增 Application 行为：

```text
approve_task_prompt(project_id, task_id)
```

后端负责：

- 解析当前 Prompt Source；
- 取得当前最终会送入 Video Provider 的 Prompt；
- 计算稳定 hash；
- 保存 approved source / hash / timestamp；
- 返回更新后的 Task Editor / Summary Read Model。

## 7.2 确认并下一个

“确认并下一个”主要是 UI 导航行为，不应创建新的领域概念。

流程：

```text
approve current task
→ 成功
→ 前端按当前可见 Task 顺序打开下一任务
```

如果保存失败、审核失败或 Task 已被其他操作改变，不得悄悄跳到下一条。

## 7.3 修改与确认

用户可以：

- 直接接受 AI Prompt；
- 编辑 AI Prompt 后确认；
- 切回用户 Prompt 后确认；
- 选择旧 AI Revision 后确认。

系统只关心“当前有效 Prompt 是否已被用户确认”。

# 8. Batch Video Generation Gate

## 8.1 批量生成默认条件

Task 默认必须同时满足：

```text
prompt_review_status == approved
AND current_prompt_hash == approved_prompt_hash
AND no active video generation job
AND generation validation passed
```

才进入批量视频生成。

## 8.2 批量提交预览

提交前后端返回或前端基于 Read Model 显示：

```text
选中 24 个任务
18 个可生成
4 个待检查
1 个正在生成
1 个参数无效
```

只有 18 个合法任务会创建 Video Job。

禁止前端为了“方便”绕过审核 Gate 直接逐项调用 generation endpoint。

## 8.3 视频 Job 仍沿用 V0.3 不可变模型

V0.4 不重做 Video Generation Job。

批量生成只是：

```text
Batch Submission / Scheduler
      ↓
existing GenerationService.submit(...)
      ↓
immutable Job
      ↓
Video Provider
      ↓
Result
```

可以新增 Generation Batch 汇总对象，但不得复制 Job / Result 领域逻辑。

---

# 9. 两类 Queue 必须独立

```text
Prompt Enhancement Queue
          │
          ├── Qwen3.8 / Prompt AI Provider
          │
          └── AiPromptRevision

Video Generation Queue
          │
          ├── ComfyUI / Video Generation Provider
          │
          └── Result
```

两类 Scheduler 独立，因此允许出现：

```text
Task 01-10 正在视频生成
同时
Task 20-30 正在做 Prompt Enhancement
```

禁止使用一个笼统 `QueueItem` 把两种完全不同的领域工作强行混在一起。

可以在 Runtime Read Model 层统一聚合显示。

# 10. Frontend Adapter / API 建议

具体路由可实现时微调，但职责建议如下。

## 10.1 Prompt Batch

```http
POST /api/v1/projects/{project_id}/prompt-enhancement-batches
GET  /api/v1/projects/{project_id}/prompt-enhancement-batches/{batch_id}
POST /api/v1/projects/{project_id}/prompt-enhancement-batches/{batch_id}/cancel
POST /api/v1/projects/{project_id}/prompt-enhancement-batches/{batch_id}/retry-failed
```

提交示例语义：

```json
{
  "taskIds": ["..."],
  "context": {
    "includeProjectBackground": true,
    "includePreviousTaskSummary": true
  },
  "providerProfileId": "local-qwen3.8"
}
```

Profile ID 只是示意，不要求硬编码该名称。

## 10.2 Prompt Review

```http
POST /api/v1/projects/{project_id}/tasks/{task_id}/prompt-review/approve
```

可选：

```http
DELETE /api/v1/projects/{project_id}/tasks/{task_id}/prompt-review
```

但正常情况下审核失效应由后端自动计算，不要求用户手动“取消确认”。

## 10.3 Batch Video Generation

建议新增批量入口，而不是 React 循环调用单任务 submit：

```http
POST /api/v1/projects/{project_id}/generation-batches
```

后端负责 eligibility 判断、创建合法 Job、返回 skip reasons 与汇总。

## 10.4 Read Model

`TaskSummary` 至少应可表达用户真正需要的轻量状态：

```text
promptEnhancementStatus
promptReviewStatus
videoGenerationStatus
hasActivePromptJob
hasActiveVideoJob
```

具体字段可进一步压缩，但 React 不应通过 Revision / Job 数组自行推导。

项目级 Runtime 建议增加：

```text
promptQueueSummary
videoQueueSummary
```

# 13. 开发阶段

## Phase C0 — Prompt Review Foundation

- PromptReviewStatus；
- approved source / hash / timestamp；
- 自动失效规则；
- TaskSummary / TaskEditorView 暴露审核状态；

### Gate C0

- 当前 Prompt 可被确认；
- 编辑有效 Prompt 后审核自动失效；
- 切换 view mode 不失效；
- 切换 Prompt Source / Revision 正确失效。

## Phase C1 — Prompt Batch Persistence

- PromptEnhancementBatch；
- PromptEnhancementJob；
- migration；
- Repository；
- 输入快照。

### Gate C1

- 批量提交后即使 Task 被修改，排队 Job 输入不变；
- Batch / Job 重启应用后仍存在；
- active duplicate 有稳定规则。

## Phase C2 — Prompt Queue Scheduler

- 单机 Scheduler；
- 默认 concurrency=1；
- Qwen3.8 Provider Profile；
- 顺序执行；
- failure / cancel / retry；
- Runtime Events。

### Gate C2

- 20 个 Task 可一次提交并逐项执行；
- 单项失败不会阻塞后续项；
- completed Job 创建 Revision 并进入待检查；
- 单任务增强仍正常。

## Phase C3 — Batch Review UI

以 `UI_V0.9_BATCH_REVIEW_WORKFLOW.md` 为准：

- 多选批量增强；
- Task Card / Table 状态；
- Prompt Queue 运行摘要；
- 上一个 / 下一个；
- 确认并下一个；
- 审核进度。

### Gate C3

- 用户无需反复关闭 / 重开编辑器即可连续审核；
- 列表与卡片模式状态一致；
- UI 不出现工程术语参数墙。

## Phase C4 — Batch Video Generation

- generation batch submit；
- eligibility / skip reasons；
- 复用现有 GenerationService / immutable Job；
- 独立 Video Queue 汇总。

### Gate C4

- 未审核任务不会被默认批量生成；
- 已审核合法任务一次加入生成队列；
- 旧 Result 不被覆盖；
- Prompt Queue 与 Video Queue 可同时运行。

## Phase C5 — Runtime / Regression

- 项目级双 Queue Runtime Read Model；
- SSE；
- Fake Prompt Provider 批量场景；
- Fake Video Provider 批量场景；
- Playwright 批量主路径。

V0.4 Freeze 至少满足：

- [ ] 默认 Qwen3.8 Prompt AI Profile 可用于正式 Prompt Enhancement；
- [ ] 单任务 AI 增强保持原有行为；
- [ ] 多 Task 可一次加入 Prompt Enhancement Queue；
- [ ] Prompt Batch / Job 持久化；
- [ ] Prompt Job 输入为不可变快照；
- [ ] 默认本地 Prompt AI concurrency = 1；
- [ ] 单个失败不会停止整个 Batch；
- [ ] 支持取消未开始项和重试失败项；
- [ ] 增强完成后 Task 进入待检查；
- [ ] 用户可确认当前有效 Prompt；
- [ ] 修改有效 Prompt / Source / Revision 后确认状态自动失效；
- [ ] Task Editor 支持上一个 / 下一个 / 确认并下一个；
- [ ] 列表与卡片模式均能清晰识别提示词状态；
- [ ] 批量视频生成默认只接受已审核且验证通过的 Task；
- [ ] 批量视频生成复用 V0.3 immutable Job / Result；
- [ ] Prompt Queue 与 Video Queue 可同时存在并独立汇总；
- [ ] 项目级 Runtime / SSE 支持双 Queue 状态；
- [ ] Unit / Integration / Contract / E2E 全部建立对应覆盖；
- [ ] UI 不恢复参数墙或复杂工程术语。

# 16. V0.4 之后

V0.4 完成后，再继续：

- 更完整的片段承接 / Task Chain；
- Context Stale 自动提示与批量重新生成；
- 手机端远程进度与失败处理；
- Provider 配置 UI；
- 多 Prompt AI Profile；
- 多 Video Provider；
- 更复杂的批量优先级与暂停 / 恢复；
- 自动化质量检查，但仍保留人工最终确认的可控模式。

V0.4 的核心价值不是“多一个批量按钮”，而是正式建立 ShotMill 的生产节奏：

> **AI 批量准备 → 人集中审核 → GPU 批量生成。**
